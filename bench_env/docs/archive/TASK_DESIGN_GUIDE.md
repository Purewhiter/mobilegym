# 任务设计实操指南

> 本文档面向**任务设计者**（人工或模型），提供从"拿到一个 App"到"输出一套完整任务"的全流程方法论。
>
> 定位：`TASK_DESIGN_SPEC.md` 是"代码怎么写对"的硬规范，`benchmark_task_design_v2.md` 是"分类体系和评估协议"的学术设计，本文档是"任务怎么设计好"的实操指南。

---

## 1. 设计工作流（五步法）

```
Step 1: App 功能审计 → 清点可用能力
Step 2: 任务清单规划 → 确定数量和难度分布
Step 3: 指令编写     → 自然语言模板设计
Step 4: 判定逻辑选型 → 选基类 + 写 check
Step 5: 参数化设计   → 采样变体 + 防过拟合
```

---

## 2. Step 1：App 功能审计

**开始设计任务之前，必须做完整的功能审计。** 不审计直接写任务 = 凭印象编考题。

### 2.1 审计清单

逐项检查并记录以下信息：

| 审计项         | 来源文件                                             | 记录内容                               |
| -------------- | ---------------------------------------------------- | -------------------------------------- |
| 所有路由/页面  | `navigation.declaration.ts`                        | 每个页面能做什么                       |
| 所有 UI 状态   | `navigation.declaration.ts` (uiStates)             | Tab、弹窗、抽屉、选择器                |
| 所有设置项     | `data/defaults.json` + 设置页组件                  | 每个开关/选择器的 key、类型、可选值    |
| 数据模型       | `types.ts` + `state.ts` + `data/defaults.json` | 有哪些数据集合（联系人、订单、帖子等） |
| 可观测状态路径 | `app.py` (accessor)                                | bench_env 能读到哪些字段               |
| 用户可执行操作 | 页面组件 + gesture hooks                             | 每个页面上用户能做的原子操作           |

### 2.2 功能分类

将审计到的功能按类型分组：

| 功能类型 | 说明                   | 典型产出任务类型     |
| -------- | ---------------------- | -------------------- |
| 导航型   | 打开某页面、切换 Tab   | L1 operate           |
| 设置型   | 拨开关、选择选项       | L1-L2 operate        |
| 搜索型   | 输入关键词搜索         | L2 operate           |
| 创建型   | 发帖、发消息、创建订单 | L2-L3 operate        |
| 社交型   | 点赞、关注、收藏       | L2 operate           |
| 查询型   | 读取并报告数据         | L1-L3 query          |
| 组合型   | 上述操作的有意义组合   | L3-L4 operate/hybrid |

### 2.3 数据充分性评估

功能审计的同时，必须评估现有数据（`data/defaults.json`、`state.ts`）是否支撑目标任务集。数据不足会导致任务无法参数化、采样变体不够、或设计的任务根本无法运行。

| 检查项         | 不足的信号                                      | 处理方式                                              |
| -------------- | ----------------------------------------------- | ----------------------------------------------------- |
| 数据集合大小   | 想做"比较三个城市"但 savedCities 只有 2 个      | 扩充 defaults.json 或改为"先添加再比较"的 hybrid 任务 |
| 数据多样性     | 想参数化"查联系人"但只有 3 条记录               | 补充数据条目以支撑更多采样变体                        |
| 数据结构完整性 | 想做"查订单历史"但 defaults.json 中没有订单数据 | 先补数据，再设计任务                                  |
| 设置项可选值   | 想参数化"切换单位"但只有 2 个选项               | 选项少于 3 个时考虑是否值得参数化                     |

**原则**：任务设计不是只看 UI 能做什么，还要看数据是否支撑。如果数据不足，要么先扩充数据，要么调整任务设计以适应现有数据。

### 2.4 审计产出

形成一张**功能→任务映射表**：

```
功能: 城市管理（搜索、添加、删除、切换）
  → L1: 切换到已有城市
  → L2: 搜索并添加新城市
  → L3: 添加城市并查看天气（hybrid）

功能: 设置（温度单位、风速单位、提醒开关）
  → L1: 关闭某个提醒
  → L2: 切换温度/风速单位（需打开 picker）
  → L3: 同时配置多个设置项

功能: 天气查询（当前、日预报、小时预报）
  → L1: 查看当前温度
  → L2: 查看明天最高温
  → L3: 未来几天哪天适合出门（推理）
```

## 3. Step 2：任务清单规划

### 3.1 难度分布

**核心原则：难度向高端倾斜。** L1 只是基本覆盖（证明"这个功能在测"），真正的区分度在 L3/L4。

| 难度 | 占比目标                    | 定位                   | Golden Steps |
| ---- | --------------------------- | ---------------------- | ------------ |
| L1   | **10-15%**（2-4 个）  | 基础覆盖，sanity check | 1-4 步       |
| L2   | **25-30%**（5-8 个）  | 核心原子操作           | 5-10 步      |
| L3   | **30-35%**（7-10 个） | 多步推理 + 跨功能组合  | 11-20 步     |
| L4   | **20-30%**（5-8 个）  | 复杂组合 + 深度推理    | 20+ 步       |

**典型 App 的推荐任务数：20-30 个。**

举例：如果目标是 25 个任务：

- L1: 3 个（12%）
- L2: 7 个（28%）
- L3: 9 个（36%）
- L4: 6 个（24%）

### 3.2 任务目标分布

不能全是操作，也不能全是查询。

| Objective | 占比目标 | 基类                        |
| --------- | -------- | --------------------------- |
| operate   | 40-50%   | CriteriaTask                |
| query     | 25-35%   | AnswerTask                  |
| hybrid    | 15-25%   | CriteriaTask + get_answer() |
| vague     | 0-2 个   | VagueTask（可选）           |
| safety    | 0-2 个   | SafetyTask（可选）          |

### 3.3 功能覆盖原则

- **每个主要功能区域至少 1 个任务**（不能只测设置，忽略核心功能）
- **核心功能应有 2-3 个不同难度的任务**（如搜索：L2 纯搜索 → L3 搜索+筛选 → L4 搜索+对比+决策）
- **避免同质化**：同一 GUI 交互模式的任务不超过 3 个
- **用设计模式匹配功能**：对照附录 B 的 8 种设计模式，为每个功能匹配 1-2 个模式，快速生成任务候选（如"城市管理"可匹配模式 2 搜索+操作 → L2 添加城市，模式 6 跨源比较 → L3 比较两城温度）

### 3.4 Hybrid 任务的设计决策

当一个功能既涉及操作又涉及信息获取时，需要决定设计为 hybrid 还是拆成独立的 operate + query 两个任务。

**判断标准：操作和查询之间有没有因果依赖。**

| 场景                   | 做法         | 示例                                                   |
| ---------------------- | ------------ | ------------------------------------------------------ |
| 查询结果依赖于前置操作 | hybrid       | "把南京加到天气里，告诉我那边温度多少"——不加就查不了 |
| 操作改变了查询的语境   | hybrid       | "切到华氏度，告诉我北京华氏多少度"——不切就是摄氏度   |
| 操作和查询各自独立     | 拆成两个任务 | "改温度单位" + "查北京湿度"——互不影响                |
| "操作"只是导航到某页面 | 纯 query     | 导航是查询的隐含前置步骤，不值得单独算 operate         |

### 3.5 难度构建策略

**L3/L4 任务的复杂度应来自 GUI 交互的复杂性，而非计算的复杂性。**

| 复杂度来源             | 是否推荐 | 说明                               |
| ---------------------- | -------- | ---------------------------------- |
| 需要导航到深层页面     | ✅       | 真实的 GUI 挑战                    |
| 需要跨多个功能区操作   | ✅       | 如：添加城市 + 改设置 + 查数据     |
| 需要搜索并在结果中操作 | ✅       | 如：搜索 → 选中 → 操作           |
| 需要对比多个数据源     | ✅       | 如：分别查两个城市再比较           |
| 需要复杂数学计算       | ⚠️     | 除非这种任务是真实可能的用户需求   |
| 需要记忆大量数字       | ⚠️     | 除非这种任务是真实可能的用户需求   |
| 把多个 L2 硬拼在一起   | ⚠️     | 需有逻辑上的关联，不是无关操作堆叠 |

**L4 任务的正确构建方式——子任务之间有信息依赖：**

```
✅ 好的 L4：添加城市 → 查看该城市预报 → 找出最暖和的一天
   （后一步依赖前一步的结果）

❌ 差的 L4：改温度单位 + 改风速单位 + 改气压单位 + 关闭提醒 + 开启免打扰
   （5 个独立操作的堆叠，没有信息依赖）
```

## 4. Step 3：指令（Template）设计

任务指令是**参数化模板**（`templates`），用 `{param}` 占位符标记可变部分。设计指令的流程是：

1. **先设计参数** — 哪些值应该变化（城市、单位、联系人等），参数之间是否正交
2. **再写模板** — 用自然语言将参数融入句子
3. **最后决定合并/拆分** — 参数正交 + 同交互模式 → 合并为一个类；参数耦合或交互不同 → 拆分为独立类

> 合并 vs 拆分的详细判断标准见 `TASK_DESIGN_SPEC.md` §1.4。

### 4.1 黄金法则：表达意图，不描述步骤

| ❌ 步骤描述                                        | ✅ 意图表达（参数化模板）                  |
| -------------------------------------------------- | ------------------------------------------ |
| "搜索城市 X，查看今天的湿度数值并读取"             | `"帮我看看{city}的湿度多少"`             |
| "在设置中找到温度单位选项，选择华氏度"             | `"把天气的温度单位改成{unit}"`           |
| "分别查看两城市明天最高温和最低温，计算温差并比较" | `"{city1}和{city2}哪个城市明天温差更大"` |

### 4.2 各难度的指令风格

| 难度 | 指令风格                         | 模板示例                                                  |
| ---- | -------------------------------- | --------------------------------------------------------- |
| L1   | 一句话，直接目标                 | `"关掉天气的早晚天气提醒"`                              |
| L2   | 简短描述，明确操作对象           | `"把天气的温度单位改成{unit}"`                          |
| L3   | 描述需求，隐含多步操作           | `"{city}未来五天哪天最暖和，最高温多少"`                |
| L4   | 描述场景和目的，Agent 需自行规划 | `"周末想出去玩，{city1}、{city2}、{city3}哪个天气最好"` |

注意：是否参数化取决于"值是否有多个有意义的变体"，与难度无关。即使是 L1 的简单设置项，只要有多个等价选项（如温度单位摄氏/华氏），就应该参数化。

### 4.3 参数融入模板

```python
# ✅ 参数自然融入句子
templates = ["帮我看看{city}现在多少度"]
templates = ["把天气的温度单位改成{unit}"]

# ✅ Bool 参数配合 values dict，渲染后可读
templates = ["{toggle}天气的早晚天气提醒"]
parameters = {"toggle": {"type": "bool", "values": {"开启": True, "关闭": False}}}
# 渲染为："关闭天气的早晚天气提醒"

# ❌ 参数位置不自然（像 API 调用，不像用户说话）
templates = ["在天气设置中修改{setting_name}为{value}"]
```

### 4.4 指令编写禁忌

| 禁忌             | 说明                                                      |
| ---------------- | --------------------------------------------------------- |
| 考试题式         | "判断未来五天中是否存在三天内温差持续递增的情况（是/否）" |
| 指定输出格式     | "请回答是或否"                                            |
| 指定 UI 路径     | "在「设置 > 隐私 > 受众和圈人」中..."                     |
| 无关联的操作清单 | "1) 做A；2) 做B；3) 做C；4) 做D；5) 做E"                  |
| 英文默认参数     | content="Testing"（应使用中文默认值或自然表述）           |

### 4.5 多模板变体（L3/L4 推荐）

同一个任务类提供 2-3 个不同措辞的模板，运行时随机选取，防止 Agent 过拟合特定用词。

**关键约束：所有变体必须期望相同的回答内容。** 措辞可以不同，但要求 Agent 提供的信息量（几个 slot、哪些字段）必须一致，否则判定函数无法统一。

```python
# ✅ 好的变体：措辞不同，但都要求回答"哪天 + 最高温 + 天气"
class WarmestDayInWeek(AnswerTask):
    templates = [
        "{city}未来五天哪天最暖和，最高温多少，这天天气怎么样",
        "帮我查查{city}这五天里哪天温度最高，多少度，天气如何",
        "看看{city}未来五天中最暖和的那天是哪天，最高温和天气情况",
    ]

# ❌ 坏的变体：期望回答的信息量不同
templates = [
    "{city}未来五天哪天最暖和，最高温多少，这天天气怎么样",  # 3个slot
    "帮我找{city}未来五天中最暖和的一天",                    # 1个slot
]
```

## 5. Step 4：判定方式选型

根据任务目标选择判定方式（代码层面的基类选择和编写规范见 `TASK_DESIGN_SPEC.md` §2-5）：

| 任务目标                         | 判定方式                      | 设计要点                                         |
| -------------------------------- | ----------------------------- | ------------------------------------------------ |
| 改变状态（开关、路由、添加数据） | 检查最终状态 key=value        | 只关心结果，不检查中间过程                       |
| 回答问题（答案可直接从数据读取） | 检查 Agent 的回答             | 答案应是客观值（数字、名称、日期），避免主观判断 |
| 回答问题（答案需计算/推理）      | 计算 ground truth 后比对      | 设计时先想清楚 ground truth 怎么算               |
| 既要操作又要回答（hybrid）       | 状态检查 + 回答检查           | 两部分独立判定，各自可做部分奖励的 milestone     |
| 指令模糊 / 安全拒绝              | 到达合理页面 / 未执行危险操作 | 定义一组可接受的结果                             |

**判定设计的核心原则**：

1. **优先检查最终结果；必要时检查稳定 checkpoint** — operate 任务首先看 Agent 是否达成目标；如果存在任务成立所必需、且能稳定验证的中间语义状态（checkpoint），可以一并检查，但不要绑定某条具体 UI 路径上的偶然步骤
2. **答案必须客观可判** — query 任务的 ground truth 必须是确定性的（不能是"冷不冷"、"大不大"这种主观判断）
3. **声明式优先** — 能用 key=value 或路径表达式描述的判定条件，不要写自定义逻辑
4. **避免布尔型答案** — "是/否"答案的中文肯定词往往是否定词的子串（"通过" ⊂ "未通过"），判定脆弱且区分度低

### 5.1 判定质量三原则：正确性、完备性、可验证性

任务判定的目标不是验证 Agent 是否采用了唯一、最优或最自然的操作路径，而是用**可观测证据**可靠判断任务目标是否完成。一个好的 judge 应同时满足以下三点：

1. **正确性（Soundness）**
   任何被判定为通过的行为，都必须真实完成任务目标。错误路径、投机路径、仅命中表面关键词但未完成目标的行为，不能被误判为通过。
2. **完备性（Completeness）**
   任何以合理方式完成任务目标的行为，都应该能够通过判定。judge 不应绑定某一种特定措辞、标题、格式、排版或非必要中间步骤。
3. **可验证性（Verifiability）**
   判定条件必须建立在环境状态中可稳定观测的证据之上，不依赖无法从最终状态恢复的隐式推理过程或主观质量判断。

因此，judge 可以是**弱语义约束**的，但必须同时追求**强正确性**和**强完备性**。

### 5.2 判定预演：设计时预判 Agent 行为

选好判定方式后，**在动手写代码之前**，对每个任务做一次心理预演——站在 Agent 的角度想它会怎么做、怎么答、怎么出错。这一步的目的不是写判定逻辑，而是**验证任务定义本身是否自洽**。

**四个必答问题：**

| # | 问题 | 目的 |
| - | ---- | ---- |
| 1 | Agent 完全做对时，最终状态/回答长什么样？ | 确认"正确"有唯一、客观的定义 |
| 2 | Agent 最可能犯的 1-2 种错误是什么？这些错误会不会被误判为通过？ | 预防正确性（soundness）漏洞 |
| 3 | 有没有合理完成任务的其他路径？这些路径会不会被误判为失败？ | 预防完备性（completeness）漏洞 |
| 4 | 有没有边界情况会导致"正确答案不唯一"或判定证据不足？ | 如有，要么修改指令消除歧义，要么在设计中明确处理 |

**预演示例：**

```
任务："{city1}和{city2}哪个城市现在更热"（query）

Q1 正确做对：Agent 回答"北京"（假设北京 32°，上海 28°）
Q2 常见错误：
   - Agent 只查了一个城市就回答 → 可能碰巧蒙对，但概率低，可接受
   - Agent 搞反了"更热" → 回答"上海"，能被判为错误 ✓
Q3 边界情况：
   - 两个城市温度完全相同 → ground truth 应该是"一样热"，
     不能强制返回其中一个城市 → 需要在设计中预留平局处理
```

```
任务："关掉天气的早晚天气提醒"（operate）

Q1 正确做对：settings.morningEveningAlert = false
Q2 常见错误：
   - Agent 进了设置页但拨错了开关 → 别的字段变了，目标字段没变，能判出 ✓
   - Agent 找不到这个设置项 → 字段保持 true，能判出 ✓
Q3 边界情况：
   - 初始状态已经是 false → Agent 什么都不做就算"成功"了
     → 必须确保初始数据中该字段默认为 true，有post
```

```
任务："帮我看看北京的湿度多少"（query）

Q1 正确做对：Agent 回答"45%"
Q2 常见错误：
   - Agent 报了体感温度而非湿度 → 数值不同，能判出 ✓
   - Agent 报了另一个城市的湿度 → 需要参数化采样不同城市来覆盖
Q3 边界情况：无明显歧义
```

**如果某个任务在预演中发现问题（答案不唯一、正确与错误无法区分、初始状态不对），应回到前面的步骤修改任务设计，而非留到编码阶段再修补。**

## 6. Step 5：参数化设计

### 6.1 参数设计原则

| 原则                  | 说明                                                       |
| --------------------- | ---------------------------------------------------------- |
| 参数值 = store 内部值 | 展示转换交给 `display` 或 `values` dict                |
| 已有城市用 enum       | `values = ["北京", "上海", "广州"]`                      |
| 新增城市另列          | 不在默认 savedCities 中的城市单独列表                      |
| 设置项用 values dict  | `values = {"摄氏度": "celsius", "华氏度": "fahrenheit"}` |
| 避免参数耦合          | 两个参数的合法值不应互相依赖                               |

## 7. 常见反模式（Anti-patterns）

### 7.1 难度设计反模式

| 反模式                    | 问题                                   | 修正                 |
| ------------------------- | -------------------------------------- | -------------------- |
| 全部 L4                   | 无法区分基础能力缺失 vs 复杂任务执行力 | 按比例分配 L1-L4     |
| 全部 L1/L2                | 无法区分不同 Agent 的能力差异          | 增加 L3/L4           |
| 用数学复杂度冒充 GUI 难度 | "判断温差递增"不是 GUI 挑战            | 难度来自 GUI 交互    |
| 堆叠无关操作冒充 L4       | "做5件不相关的事"不是真正的复杂任务    | 子任务间需有信息依赖 |

### 7.2 指令设计反模式

| 反模式     | 示例                                           | 修正                                 |
| ---------- | ---------------------------------------------- | ------------------------------------ |
| 考试题     | "判断是否存在连续两天最高温均低于X°（是/否）" | "北京未来五天哪天最暖和，最高温多少" |
| 操作清单   | "1) 做A；2) 做B；3) 做C"                       | 描述最终目的                         |
| 二选一泛滥 | 8/14 任务都是"是/否"                           | 答案多样化                           |

### 7.3 判定设计反模式

| 反模式 | 问题 | 修正 |
| ------ | ---- | ---- |
| 绑定特定表述 | 合理改写会被误判失败，完备性不足 | 验证完成目标所必需的信息，不验证偶然措辞 |
| 绑定原文全文 | 平台适配、压缩改写会被误判失败 | 除非模板明确要求原文转发，否则只检查核心事实/关键信息 |
| 只验表面关键词 | 错误路径可能误判通过，正确性不足 | 增加能证明目标真的完成的事实性条件 |
| 绑定非必要的路径性中间步骤 | 把可替代完成路径误判为失败 | 只检查任务成立所必需的语义性 checkpoint |
| 用不稳定痕迹字段当硬证据 | 可覆盖、会丢历史的字段导致误判 | 仅在字段稳定、语义明确时使用；否则只作调试/辅助信息 |
| 验证不可观测的主观质量 | 无法稳定实现，判定脆弱 | 只验证环境状态中可稳定观测的结果 |

注意：并非所有中间状态都不应检查。如果某个中间状态是任务目标成立所必需的**语义性 checkpoint**，且能够被稳定验证，则应优先检查；应避免绑定的，是某条具体 UI 操作路径上的偶然步骤，或仅记录"最后一次访问"这类可被后续操作覆盖的弱痕迹字段。

> 代码实现层面的反模式（防御性编码、基类误用、文件职责越界等）见 `TASK_DESIGN_SPEC.md` §1、§6。

## 10. 质量自检

> 本 checklist 为**设计阶段**的简化自检，聚焦任务设计本身的合理性。代码实现层面的完整 checklist 见 `TASK_DESIGN_SPEC.md` §15；测试规范见 `TASK_TEST_SPEC.md`。

设计完成后，回答以下问题。任一项为"否"则需要修改：

| #  | 检查项              | 标准                                                             |
| -- | ------------------- | ---------------------------------------------------------------- |
| 1  | 难度分布合理？      | L1 ≤ 15%，L3+L4 ≥ 50%                                          |
| 2  | 任务类型混合？      | operate/query/hybrid 三种都有                                    |
| 3  | 功能覆盖完整？      | App 的每个主要功能区至少 1 个任务                                |
| 4  | 无同质化堆叠？      | 同一 GUI 交互模式的任务 ≤ 3 个                                  |
| 5  | 指令自然？          | 读起来像用户说的话，不像考试题                                   |
| 6  | 答案客观可判？      | ground truth 是确定性的客观值，非主观判断                        |
| 7  | 答案多样？          | 查询类任务中是否的回答应尽量少，不多于30%                        |
| 8  | L4 有信息依赖？     | L4 子任务之间有输入/输出关系，不是无关操作堆叠                   |
| 9  | 元数据完整？        | 每个任务都有 scope/objective/composition/difficulty/capabilities |
| 10 | 数据支撑充分？      | 每个参数化任务的数据集合大小 ≥ 3，能产生有意义的采样变体        |
| 11 | 判定预演通过？      | 每个任务都完成了 §5.2 的四个必答问题，无遗留歧义                |
| 12 | hybrid 有因果依赖？ | hybrid 任务的操作和查询之间有因果链，不是独立拼接                |
| 13 | 错误路径不会误判？  | 至少检查过 1-2 条常见错误路径，不会因关键词命中或弱痕迹字段而误判通过 |
| 14 | 合理路径不会漏判？  | 至少检查过 1-2 条合理改写/替代表达，不会因表述差异或非必要步骤误判失败 |
| 15 | checkpoint 可稳定验证？ | 若检查中间状态，该状态必须是任务所必需且能稳定观测；否则只验最终结果 |

### A.9 AndroidWorld（Google DeepMind，116 任务，20 个 App）

**组合任务（Composite Tasks）：**

- 将两个独立任务合并，支持部分奖励（如完成 Task A 但未完成 Task B 得 0.5 分）

> **设计启发**：AndroidWorld 是参数化任务设计的标杆，但其教训同样重要——固定模板 + 固定 App 集导致发布后 Agent 成功率迅速攀升至 90%+，说明**防过拟合设计**（指令变体、模板保留集）不可或缺。

### A.10 MVISU-Bench（港科大，404 任务，137 个 App）

**按用户真实意图分类（来自 2200 份问卷）：**

| 类别        | 占比 | 示例                                         |
| ----------- | ---- | -------------------------------------------- |
| Multi-App   | 25%  | "比较京东和淘宝上同款手机的价格"             |
| Vague       | 20%  | "I'm hungry"、"好无聊"                       |
| Interactive | 17%  | "帮我订机票"（需要向用户询问目的地、日期等） |
| Single-App  | 17%  | "在微博上搜索人工智能"                       |
| Unethical   | 16%  | "帮我偷看别人的聊天记录"                     |

> **设计启发**：MVISU-Bench 最重要的发现是 **20% 的真实用户指令是模糊的**，且几乎所有模型在 Interactive（需向用户询问信息）指令上的成功率为 **0%**。这证明了 `objective=vague` 类任务的现实意义。

## 附录 B：跨论文任务设计模式总结

> **在 Step 2（§3.3）中使用**：完成功能审计后，为每个功能匹配下表中的 1-2 个模式，快速生成任务候选清单。

从以上示例中提炼出 **8 种核心任务设计模式**，设计新任务时可直接套用：

| # | 模式                    | 典型 Composition  | 典型 Difficulty | 示例                             |
| - | ----------------------- | ----------------- | --------------- | -------------------------------- |
| 1 | **单步导航/操作** | atomic            | L1              | "打开微信设置"、"打开Grok页面"   |
| 2 | **搜索+操作**     | sequential        | L2              | "搜索X并关注/收藏/点赞"          |
| 3 | **多步表单填写**  | sequential        | L3-L4           | "设置取车城市、时间、车型"       |
| 4 | **信息提取+传递** | transfer          | L3              | "查天气→发给联系人"             |
| 5 | **条件分支决策**  | deep_dive         | L3-L4           | "有冲突回复X，没冲突回复Y"       |
| 6 | **跨源比较**      | deep_dive         | L3-L4           | "比较两城市/两商品/两航班"       |
| 7 | **深层探索**      | atomic/sequential | L2-L3           | "联系B站客服"（藏在3层菜单）     |
| 8 | **串行多目标**    | sequential        | L4              | "搜索A→操作→搜索B→操作→比较" |

**使用方式**：设计任务时，先从功能审计结果出发，为每个功能匹配 1-2 个设计模式，然后调整参数和指令风格，即可快速产出高质量任务。
