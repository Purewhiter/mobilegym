# Mobile Gym 重构救援

这个 skill 处理的是“代码没有立刻坏，但继续堆功能会越来越糟”的区域。目标不是大改重写，而是在不破坏现有行为、导航约定和 benchmark 契约的前提下，把局部从失控状态拉回可维护状态。

## Quick Start

开始前先写清楚：

1. 哪些行为绝对不能变
2. 这次只救哪 1 到 2 个坏味道
3. 最小切口是什么
4. 删除或搬移代码后怎么验证没回归

如果核心问题集中在 React 组件 API、boolean props 膨胀、状态提升或复合组件结构，优先同时参考 `mobile-gym-react-component-governance`。

## 救援优先级

优先救这些问题：

- 未来每次改动都会继续放大的结构问题
- source of truth 不清导致的状态混乱
- 重复业务规则导致的分支漂移
- 页面/组件承担了错误层级的职责

不要优先处理这些伪问题：

- 单纯“文件看起来长”
- 没有带来修改成本的样式细节
- 只为了更优雅命名或抽象的重排

## 1. 先判断是不是“救援型重构”

满足任意几条，就按救援型重构处理：

- 单个组件或页面过大，渲染、状态、事件、副作用混在一起
- 同一业务规则散落在多个分支或多个文件里
- URL、导航状态、弹窗状态和本地 state 纠缠
- `constants.ts`、`data/defaults.json`、`state.ts` 职责混乱
- 为了“先跑起来”塞入了临时逻辑，但后续功能都在绕着它写
- 改一处经常牵出多处脆弱联动

如果用户要的是行为升级，不是结构治理，先用 `mobile-gym-feature-design`，不要误把功能开发做成重构。

## 2. 先冻结“不能变的东西”

重构前先列出这些不允许变化的内容：

```markdown
保留行为:
- ...

保留契约:
- 路由 / transition / data-trigger / data-action / state path / bench path

本次允许变化:
- 文件拆分
- 提炼函数
- 移动代码到正确层
- 删除确定无用的死代码
```

如果无法清楚描述“什么必须不变”，不要开始重构。

## 3. 找出最危险的坏味道

每次只选 1 到 2 个核心坏味道，不要全都一起修：

- 职责混杂：页面既拥有数据定义，又处理运行时逻辑，还直接渲染复杂 UI
- 重复分支：同一规则在多个 `if` / `switch` 中复制粘贴
- 边界漂移：默认值、配置、临时状态放错层
- 导航泄漏：应进入路由的状态被留在组件本地 state
- store 反模式：查询型 getter action、函数订阅、难以追踪的数据派生
- 视图耦合：一个局部视觉修改需要改多个无关模块

不要把“文件长”误判成核心问题。先找最影响未来修改成本的那个点。

## 4. 选择最小救援切口

优先选择这类切口：

1. 先抽纯函数或类型，不改行为
2. 再把默认数据、结构配置、运行时逻辑放回正确层
3. 再拆子组件或 hooks
4. 最后再删除被替代的旧路径或死代码

避免一口气做这些高风险动作：

- 改行为同时改结构
- 改文件职责同时改命名体系
- 改导航路径同时大规模搬组件
- 没有验证就先删一批“看起来没用”的代码

## 5. 按仓库边界做归位

救援时始终按这个方向收敛：

- 静态结构回到 `constants.ts`
- 可替换默认数据回到 `data/defaults.json`
- 运行时逻辑和临时 UI 状态回到 `state.ts`
- 路由、modal、tab、UI state 回到 `navigation.declaration.ts`
- 图标回到 `res/icons.tsx`，只使用 `Ic*`
- 业务页面使用 `navigation.ts` 的 `go()` / `back()`

发现被禁止模式时，优先替换掉：

- `Date.now()` / `new Date(...)`
- `navigator.geolocation`
- 不该出现的原始网络访问
- Zustand 查询型 getter action
- 应进 URL 的状态却只存在于 React 本地 state

## 6. 用“保行为”方式拆代码

优先使用这些低风险重构手法：

- 提炼纯渲染片段为小组件
- 提炼分支判定为命名明确的纯函数
- 提炼重复 mapping / formatting / filtering 逻辑
- 把一段本就独立的副作用抽成 hook
- 把混在 UI 文件里的结构数据移回数据层

慎用这些高风险手法，除非验证非常明确：

- 一次性改多个状态来源
- 在同一次提交里同时重写路由模型和组件结构
- 合并看似相似但边界并不相同的业务分支
- 为了“更优雅”引入抽象层或通用框架

## 7. 删除代码前先证明它真的死了

只有在满足以下条件时才删除：

- 已有新路径完全覆盖原逻辑
- 没有可见调用点或声明依赖
- 不会破坏 `navigation.declaration.ts`、`bench_env`、状态路径或生成产物

如果只是“看起来没用了”，先标记并向用户说明，不要静默删除。

## 8. 重构后的专属检查项

每次救援完成后，至少检查：

- 行为是否保持一致
- 文件职责是否比之前更清晰
- 新增的抽象是否真的降低复杂度，而不是转移复杂度
- 是否引入了额外 state source of truth
- 是否破坏导航声明、gesture tags、scroll containers
- 是否动到了 benchmark 可见路径

## 9. 选择合适的验证

- 改了导航或 UI state：运行 `node scripts/build_nav_artifacts.mjs <AppName>`
- 大型跨文件重构或结构调整：运行 `npx tsc --noEmit`
- 改了运行时代码：运行 `npm run lint` 或对应范围检查
- 小范围救援：至少手动走通原始问题路径，并检查 IDE 诊断

这个仓库里不要运行 `npm run build`。

## 10. 用“救援报告”收尾

完成后用这四点汇报：

- 本次救援的核心坏味道是什么
- 采用了哪个最小切口
- 哪些行为和契约被明确保留
- 还剩哪些脏点没有动，为什么暂时不动
