# Mobile Gym 开工闸门

用于复杂任务的开始阶段。目标不是立刻给出“能跑”的解，而是先确认这次工作到底该做到哪、受什么约束、应该调用哪个项目 skill，以及如何避免重复踩坑。

## Quick Start

开始前先做这 6 步：

1. 识别任务类型：`分析` / `设计` / `实现` / `debug` / `review` / `提交`
2. 复述用户边界：是否 `只读`、`先分析`、`不要改`、`不要提交`、`没问题再提交`
3. 找约束来源：规范文档、方案文档、现有实现、用户贴出的代码/日志/截图
4. 判断主问题类型：`语义` / `架构` / `交互` / `bench 判定`
5. 写出单一因果链：`现象 -> 根因 -> 为什么这次修法不是补丁`
6. 再决定要不要进入编辑、测试或 review

## 1. 先选对项目 skill

按任务性质立即补读对应 skill：

- 状态、数据、导航、文件职责、跨层契约：`mobile-gym-boundary-guard`
- 新功能、跨文件方案、导航或 state 契约调整：`mobile-gym-feature-design`
- React 页面/组件/hook/provider 结构治理：`mobile-gym-react-component-governance`
- 保行为整理脏代码、拆组件、去重复：`mobile-gym-refactor-rescue`
- review、audit、查风险、过一遍改动：`mobile-gym-review-gate`

如果命中了这些场景，不要只提到 skill，必须立即读取并遵循。

## 2. 先问自己这 5 个问题

- 用户现在要的是分析、方案、修改、review 还是提交？
- 用户有没有明确限制边界，比如先别改、只看我发的内容、不要重写历史？
- 这次问题是“实现错了”，还是“语义/契约本身没闭合”？
- 现在打算做的是统一方案，还是偷偷给某个 App/页面加特判？
- 这次改动完成后，哪些文档、生成物、bench 路径或 state shape 也必须一起闭合？

## 3. 识别高风险反模式

出现下面任一信号时，先停下来重想方案：

- 准备加双保险、补丁、额外 fallback、兼容旧逻辑
- 准备放宽 judge、改采样或绕过验证来“让它先过”
- 准备把逻辑塞进更顺手但职责不对的文件
- 准备用 UI 展示格式反推任务语义或 judge 语义
- 准备给单个 App、单个任务、单个页面加特殊分支
- 没有验证证据却想直接下“没问题”结论

## 4. 建立单一因果链

动手前，用 3 句以内写清：

- 现象：用户实际看到的错误是什么
- 根因：最可能的唯一主因是什么
- 修法：为什么这次改动是在修根因，而不是堆补丁

如果这 3 句写不出来，先不要改代码。

## 5. 保证语义闭合

重点核对这些链路是否一致：

- 用户说的目标语义
- 页面文案、类名、字段名、路由语义
- 状态/数据结构与默认值
- bench judge / criteria / answer / expected changes
- 文档、README、生成物、声明文件

任何一环没闭合，都不要把任务当成“只是改个 bug”。

## 6. 验证计划要前置

按改动类型提前决定验证：

- 导航/声明/页面结构：相关声明、自检脚本、产物重建
- 运行时代码：必要的 lint、类型检查、手动路径验证
- `bench_env`：至少验证任务语义、state 路径、judge 口径和失败分支
- review：先列发现，再给总结；没有证据就明确写测试缺口

## 7. 对用户汇报时的默认顺序

1. 你理解的请求边界
2. 你锁定的问题类型与主因
3. 你准备采用的统一修法或分析路径
4. 验证方式或仍存在的不确定点

不要一上来就开始改，也不要先给乐观结论。
