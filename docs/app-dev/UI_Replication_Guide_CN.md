# 模拟器 App UI 对齐真机：通用工作流

## 前言

本文档定义一套**与具体 App 无关**的工作流程，用于指导 AI Agent 发现并消除模拟器（Web Simulator）与真机之间的 UI 差异。

核心原则：**截图发现问题，工具量化差异，数据驱动修改。**

---

## 工作流总览

```
截图对比（发现差异）──→ 布局工具精确测量 ──→ 修改代码 ──→ 截图+工具双重验证 ──→ 完成
```

每一轮修改只解决**一个层次**的问题，不要跨层混改。

---

## 第一步：截图对比，发现差异

1. 用 `adb_screenshot` 截取真机当前页面。
2. 用 `mobile_screenshot` 截取模拟器同一页面。
3. 对两张图进行**纯描述性**拆解，按以下层级逐层对比：

| 对比维度 | 检查内容 |
|----------|----------|
| **数量** | 真机显示几个列表项/Tab/图标？模拟器几个？ |
| **位置** | 元素的上下左右位置是否一致？间距的松紧感觉是否一致？ |
| **比例** | 各区域占屏幕高度的比例是否一致？元素宽高比是否一致？ |
| **颜色** | 背景色、文字色、强调色是否一致？ |
| **文字** | 粗细、大小关系、对齐方式是否一致？ |
| **图标** | 形状（实心/线条）、大小是否一致？ |

> **规则**：如果无法获取真机截图，必须向用户索要，不得凭记忆或经验补全。

此步骤的输出是**差异清单**（哪些区域/元素有问题），但不需要精确像素值。

---

## 第二步：布局工具精确测量

对第一步发现的差异，使用 MCP 工具获取**归一化到 360×800 视口的精确坐标**：

- **真机端**：`adb_get_layout_elements` — 通过 uiautomator dump + 密度换算
- **模拟器端**：`mobile_get_layout_elements` — 通过 DOM 元素遍历

两端返回统一格式：`{ tag, id, text, bounds: {x, y, width, height} }`

### 操作方法

1. **并行调用**两个工具，获取元素列表
2. 按 `text` 字段匹配同名元素
3. 对比 `bounds` 数值，制作差异表格（包含 x, y, width, height 和差值）
4. **差异 ≤ 3px 视为对齐**，更大差异必须修复
5. 可传入 `selector` 参数聚焦特定区域（如 `.fixed` 只看固定定位元素）

> **关键**：必须先拿到精确数据，再修改代码。绝不能凭目测猜像素值。

此步骤的输出是**精确差异表格**（每个元素差多少像素）。

---

## 第三步：修改代码

根据第二步的精确数据修改代码。按以下优先级排序：

1. **结构差异** — 元素缺失/多余、层级关系错误
2. **位置差异** — 坐标偏移（影响全局布局）
3. **尺寸差异** — 宽高不匹配
4. **颜色差异** — 视觉风格偏差
5. **文字/图标差异** — 排版细节

**每修改一个差异后，立即进入第四步验证，确认后再改下一个。**

---

## 第四步：截图 + 工具双重验证

每次代码修改后：

1. `mobile_screenshot` 截图 — 确认视觉效果正确，无色差/错位
2. `mobile_get_layout_elements` 获取数据 — 确认数值与真机精确匹配
3. 如果仍有差异，回到第三步继续修改

**两个都通过才算完成。** 截图能发现工具检测不到的视觉问题（如颜色、透明度），工具能发现肉眼看不出的像素偏移。

---

## AI Agent 常见错误模式（必须警惕）

| 错误模式 | 表现 | 正确做法 |
|----------|------|----------|
| **不对比数据就改代码** | 看了截图觉得"差不多"就直接写 CSS | 必须先用布局工具获取精确数值 |
| **凭经验猜颜色/尺寸** | 不看截图，直接写 `text-gray-500` | 从真机截图取色，或用工具测量 |
| **一次改太多** | 同时调整颜色、间距、字体、布局 | 每次只改一个维度，改完验证 |
| **改了不验证** | 改完代码直接汇报"已完成" | 必须截图 + 工具数据双重确认 |
| **大约一致就放过** | "差 5px 应该没关系" | 差异 > 3px 必须修复 |
| **硬编码系统值** | TabBar 底部间距写死 `16px` | 引用 `DEVICE_CONFIG.bottomGestureHeight` |

## 实战经验：常见布局差异模式

以下是从 Railway12306 首页对齐实战中总结的常见差异模式及修复方法：

### 1. 底部 TabBar 与系统导航栏

**问题**：真机 TabBar（h=55）位于系统导航栏（16px）上方（y=729），模拟器 TabBar 用 `fixed bottom-0` 贴到屏幕底部（y=745），差 16px。

**修复**：TabBar 使用 `bottom: DEVICE_CONFIG.bottomGestureHeight` 定位；底部手势区背景由页面自身补齐，手势条前景通过 `data-navigation-bar-foreground="dark|light"` 单独声明。

```jsx
<div
  className="fixed left-0 right-0 bg-[#F9F9F9] ..."
  style={{ bottom: DEVICE_CONFIG.bottomGestureHeight }}
  data-navigation-bar-foreground="dark"
>
```

**注意**：不要用 `bottom-0 + 大 padding` 的方式让 TabBar 背景覆盖手势区，这会导致 TabBar 高度（71px）不匹配真机（55px）。

### 2. 多余的内边距导致累积偏移

**问题**：容器有 `pb-2`（8px），导致下方所有元素整体下移 8px，且偏移一路累积到页面底部。

**修复**：对比精确数据后移除多余 padding。

**教训**：容器的 padding 会向下游传递偏移，修改后要验证页面底部元素是否也对齐。

### 3. 网格项目高度不匹配

**问题**：真机网格项目 72.3px 高、无行间距。模拟器项目 51px + 16px gap，总高度差 30px。

**修复**：
```css
/* 错误 — 紧凑项目 + 大间距 */
.grid { gap-y: 16px; }
.item { /* 自然高度 51px */ }

/* 正确 — 固定高度 + 无间距 */
.grid { gap-y: 0; }
.item { height: 72px; padding-top: 15px; }
```

### 4. Tab 等分 vs 靠左排列

**问题**：真机三个 Tab 等分容器（各 113.3px），模拟器用 `flex gap-6` 导致 Tab 靠左聚集。

**修复**：每个 Tab 子元素添加 `flex: 1`。

### 5. 透明顶栏叠加 Banner

**问题**：真机顶栏是透明的，浮在 Banner 上方（两者都从 y=0 开始）。模拟器实现为实心顶栏 + Banner 在下方。

**修复**：Banner 从 y=0 开始，顶栏用 `position: absolute; top: 0; z-index: 20` 浮在其上。

### 6. 系统配置值应引用而非硬编码

**问题**：App 硬编码 `bottom: 16px`、`pb-[22px]` 等值，如果 `bottomGestureHeight` 配置改变，这些值不会自动更新。

**修复**：始终引用 `DEVICE_CONFIG` 中的系统值：
```jsx
import { DEVICE_CONFIG } from '../../os/data/osConfig';

// 引用系统配置
style={{ bottom: DEVICE_CONFIG.bottomGestureHeight }}
style={{ paddingBottom: DEVICE_CONFIG.bottomGestureHeight + 55 + 'px' }}
```
