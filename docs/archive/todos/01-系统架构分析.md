# mobile-gym 系统架构问题深度分析

---

## 1. 模块组织与层次分离问题

### 问题一：`AppStateRegistry.ts` 违反分层边界（严重）

**文件路径**: `os/AppStateRegistry.ts`

`os/` 层的文件直接向上导入所有 28 个 app 的数据模块：

```ts
// os/AppStateRegistry.ts L4-L26
import { NOTES_CONFIG } from '../apps/Notes/data';
import { BILIBILI_CONFIG } from '../apps/Bilibili/data';
import { WECHAT_CONFIG } from '../apps/Wechat/data';
// ... 共 18 个 app 的直接导入
import { loadWeatherState } from '../apps/Weather/utils/weatherStore';
import { getEntitiesSync } from '../apps/RedBook/data/loader';
```

按照架构意图，`os/` 是底层系统，`apps/` 是上层应用，但 `AppStateRegistry.ts` 在 os 层直接依赖了所有 app 的数据层。这造成：

1. **单向依赖原则被破坏**：os 层应该对 apps 完全无感知，但现在 os 层会随每个新 app 添加而改动。
2. **编译膨胀**：任何一个 app 的 `data/index.ts` 改变，`AppStateRegistry.ts` 会被重新编译。
3. **循环依赖风险**：如果某个 app 的 `data/index.ts` 再引用 os 层工具（如 `TimeService`），就形成了 `os → apps → os` 的循环。事实上已有：

```ts
// apps/Notes/data/index.ts L3
import * as TimeService from '../../../os/TimeService';
// apps/Wechat/data/index.ts L12
import * as TimeService from '../../../os/TimeService';
// apps/TencentMeeting/data/index.ts L1
import * as TimeService from '../../../os/TimeService';
```

这意味着 `os/AppStateRegistry.ts` → `apps/Notes/data` → `os/TimeService` 这条链已经是真实的间接循环。

---

### 问题二：`OSContext.tsx` 中的 `waitForData` 直接导入 app 数据加载器（中等）

**文件路径**: `os/OSContext.tsx` L618-L625

```ts
waitForData: async (appIds?: string[]) => {
  // ...
  if (has('redbook')) tasks.push(
    import('../apps/RedBook/data/loader').then(async m => { await m.loadEntities(); })
  );
  if (has('bilibili')) tasks.push(
    import('../apps/Bilibili/data/loader').then(m => m.preloadAll())
  );
```

OS Context 层直接硬编码了特定 app 名字和 app 专属加载器的导入逻辑。这种设计要求每次新增支持懒加载的 app 都必须修改核心 OS 文件，耦合性极高，也违反了 Open/Closed 原则。

## 2. 全局 window API 设计问题

### 问题三：__APP_NAVIGATE__ / __APP_BACK_HANDLER__ / __APP_ROUTE__ 的单例覆盖问题（严重）

**所有 App 的 NavigationHandler 组件**都共用同一个 window key：

```ts
// apps/Railway12306/Railway12306App.tsx L93-94
(window as any).__APP_BACK_HANDLER__ = handleBackPress;
(window as any).__APP_NAVIGATE__ = (path: string) => navigate(path, { replace: true });
```

当 SystemShell 同时挂载多个 app（`display:none` 方式保活），**最后挂载的 app 会覆盖这些全局单例**。由于 React Strict Mode 等原因，挂载顺序不保证稳定。

项目虽然为此引入了 `__APP_NAVIGATORS__`（一个 appId → fn 的 Map），但只有 **Alipay** 实现了这个方案：

```ts
// apps/Alipay/components/AlipayNavigationHandler.tsx L38-41
if (!(window as any).__APP_NAVIGATORS__) (window as any).__APP_NAVIGATORS__ = {};
(window as any).__APP_NAVIGATORS__['alipay'] = (path: string) => {
  navigate(path, { replace: true });
};
```

其余 21 个 app 仍使用 `__APP_NAVIGATE__` 单例写法，**在多 app 后台运行时会产生不可预期的导航目标错乱**。

`OSContext.tsx` 自身在 `navigateToAppRoute` 中也有兼容逻辑：

```ts
// os/OSContext.tsx L310-312
const registry = (window as any).__APP_NAVIGATORS__;
const fn = registry?.[appId] ?? (window as any).__APP_NAVIGATE__;
if (fn && typeof fn === 'function') { doNavigate(fn); }
```

这里的 fallback 到 `__APP_NAVIGATE__` 在多 app 并发时就会取到错误的 app 的导航函数。

### 问题四：__OS__ 在每次 state 变化时都被重新赋值（性能问题）

**文件路径**: `os/OSContext.tsx` L784

```ts
}, [state, launchApp, goHome, showRecents, closeApp, setBrightness, setVolume]);
```

整个 `__OS__` 对象（含所有方法的闭包）在 `state` 每次变化时都被重新创建和赋值。OS 状态每次 dispatch 都会触发这个 effect，导致大量不必要的对象创建。agent 或 app 如果持有了旧的 `__OS__` 引用，调用 `__OS__.getState()` 时只能获得闭包时刻的 snapshot 而非最新值。

### 问题五：全局 API 全部使用 `(window as any)` 缺乏类型安全

虽然文件末尾有局部类型声明，但整个项目中消费这些 API 的地方全部使用 `(window as any).__XXX__`，没有任何 TypeScript 类型保护。接口变更时不会有编译错误，只会在运行时失败。

## 3. App 注册与生命周期问题

### 问题六：Notes App 违反 navigation 规则（完全绕过 go()/back() 抽象）

**文件路径**: `apps/Notes/pages/*.tsx`

Notes app 的所有页面组件全部直接使用 `useNavigate()`，而不是 `useAppNavigate()` 提供的 `go()`/`back()` 封装。Weather app 同样存在此问题（8 处 useNavigate）。

这绕过了 `navigation.declaration.ts` 的约束，使得导航声明与实际代码不一致。

### 问题七：QQMusic 的 registerAppState 暴露了错误的 key 结构（数据不一致）

**文件路径**: `apps/QQMusic/context/QQMusicContext.tsx` L37

```ts
registerAppState('qqmusic', () => ({ qqmusic: state }));
```

但 `AppStateRegistry.ts` 中的 `persistentReaders.qqmusic` 返回的是扁平结构。运行时（app 挂载后）通过 `__SIM__.getState().apps.qqmusic` 返回 `{ qqmusic: { currentSong, ... } }`（多套了一层），而非挂载时通过 persistentReader 返回的扁平结构。这种不一致会导致 bench_env 的评判逻辑随 app 是否挂载而返回不同结构的数据。

### 问题八：Ebay context 的 registerAppState 使用空依赖数组（stale closure）

**文件路径**: `apps/Ebay/context/EbayContext.tsx` L129-132

```ts
useEffect(() => {
  registerAppState('ebay', () => stateRef.current);
  return () => unregisterAppState('ebay');
}, []); // 空依赖数组
```

## 4. 导航系统问题

### 问题九：navigation.ts 中的 go() 在 `from` 约束检查失败时会抛出异常

**文件路径**: `apps/Wechat/navigation.ts` L33-37

```ts
if (!matchFrom(t.from, location.pathname, searchParams)) {
  throw new Error(
    `Transition "${id}" not allowed from "${location.pathname}${location.search}"`,
  );
}
```

在 agent 测试中，如果 app 处于某个 `from` 约束不匹配的状态时调用 `go()`，会产生未捕获的运行时错误，可能导致 React 树崩溃（没有 ErrorBoundary 包裹）。

### 问题十：MemoryRouter 的 navigateToAppRoute 依赖 polling + event 双机制，存在竞态

**文件路径**: `os/OSContext.tsx` L282-330

使用了 polling（16ms 间隔）加 CustomEvent 双路导航：
1. `Date.now()` 替代了 `TimeService.now()`
2. 5 秒超时后只打印 warn 而不通知调用方
3. polling 中还有 event listener 未清理的情况

## 5. 状态管理问题

### 问题十一：Settings/Gallery/Weather/Clock 等 app 没有注册 AppStateRegistry

bench_env 调用 `__SIM__.getState().apps.settings` 时只会得到 `undefined`，无法进行状态评判。

### 问题十二：多个 app 直接在 context 中使用 `Date.now()`，违反 TimeService 规则

```ts
// apps/X/context/XContext.tsx L425
id: `new_${Date.now()}`,
// apps/TencentMeeting/context/MeetingContext.tsx L396
time: Date.now(),
// apps/Contacts/context/ContactsContext.tsx L82
const now = Date.now();
```

在模拟时间模式下，这些 app 生成的时间戳会与系统模拟时间不一致。

### 问题十三：AppStateRegistry 中 `railway12306` 的 persistentReader 直接使用 `new Date()`

**文件路径**: `os/AppStateRegistry.ts` L422

```ts
date: data?.date ?? new Date().toISOString().slice(0, 10),
```

## 6. 服务层问题

### 问题十四：TimeService 使用模块级可变变量，缺乏并发保护

模块级可变全局状态（mutable module-level globals），且在模块加载时（而非 React 挂载阶段）向 window 注册接口，没有清理机制。LocationService 也有同样问题。

### 问题十五：NetworkService 对非字符串 body 的处理不透明

对于 `FormData`/`Blob`/`ArrayBuffer` 等非字符串 body，会被静默丢弃，导致 POST 请求在不知情的情况下丢失 body 数据。

---

## 7. 类型系统问题

### 问题十六：AppId 与 ImplementedAppId 双联合类型需要同步维护

`phone` 只在 `AppId` 中有定义，但没有 manifest 也没有 AppComponents 条目。`isValidAppId('phone')` 返回 `false`，但 TypeScript 类型认为合法——类型与运行时不一致。

### 问题十七：navigation.types.ts 在多个 App 间完全重复（16 份相同文件）

### 问题十八：DeviceConfig 将视觉/UI 常量与系统行为配置混合在单一接口中

手势响应参数、视觉装饰尺寸、z-index 层叠、系统时间/位置模式、AI 服务配置、主题——全在一个 "God Object" 接口中。
