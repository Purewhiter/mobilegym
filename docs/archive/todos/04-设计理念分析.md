# mobile-gym 设计理念与概念问题深度分析

---

## 一、AOSP 仿真忠实度：Web 范式的渗漏

### 1.1 res/ 资源体系：命名像 Android，本质仍是 TypeScript

`res/colors.ts` 中出现了 Tailwind 工具类字符串作为颜色名：

`apps/Wechat/res/colors.ts` 第 100-119 行：
```ts
'tw-text-gray-400': '#9ca3af',
'tw-bg-gray-50': '#f9fafb',
'wechat-app-border-bottom-4c4c': '#4c4c4c',
```

这些连字符 key 直接暴露了 Web 实现细节：Tailwind 的工具类命名污染了 Android 风格的资源层。

**`data/index.ts` 超出了"数据入口"的职责：**

Wechat 的 `data/index.ts` 包含运行时逻辑：负时间戳解析、资产 URL 重写、聊天时间线格式化。远超 Android 中 `res/raw/` 或 `assets/` 的语义——实质上是一个**数据转换管道**，被伪装成资源层。

**`dimens.ts` 中出现了无语义名称的"任意值迁移"：**

`apps/Wechat/res/dimens.ts` 第 109-207 行：
```ts
discoverSearchWidth_1: 1,
itemWidth_24: 24,
settingsBlacklistWidth_40: 40,
meMomentsAlbumWidth_70: 70,
```

这些 `name_value` 反模式：名字里带数字值，等于没有语义抽象。

### 1.2 Android 系统服务仿真中的根本性缺口

每个 App 直接读写自己的 localStorage key，互相隔离。**没有跨 App 数据共享的抽象层**（ContentProvider）：联系人在 Contacts app 里，微信的联系人是 `wechat.contacts`，两者完全独立。

`AppStateRegistry.ts` 需要**硬编码导入每一个 App 的 CONFIG**。在真实 Android 中，`PackageManager.getInstalledPackages()` 是运行时发现机制，此处则是编译时手动注册。

## 二、Agent 可观测性：设计不一致，存在结构性盲区

### 2.1 `data-trigger` vs `data-action` 的分裂问题

设计了两种标签体系（trigger 和 action），概念合理，但执行层面存在重大漏洞：大量 `onClick` 直接绑定，未经过 `bindTap/bindLongPress`，在 DOM 中没有 `data-trigger` 标记。

更根本的问题：**Agent 实际上不通过 `data-trigger` 属性来决策，而是通过截图+坐标操作**。`data-trigger` 系统对 VLM 型 Agent 没有直接价值，主要用于静态导航图生成。DOM 标记体系为静态分析服务，而 Agent 交互体系为像素操作服务，两者之间没有桥梁。

### 2.2 Settings App 显式违反导航规则

`apps/Settings/SettingsApp.tsx` 第 28 行及 `SettingsMainPage.tsx`、`WifiNetworksPage.tsx` 等文件中直接使用 `useNavigate()`。

### 2.3 `__SIM__.getState()` 的观测性张力

优先用运行时注册的 getter，否则用 localStorage 的持久化 reader。**状态一致性是条件性的，取决于 App 是否挂载**。

典型例子：`wechat_reading` 持久化 reader 直接忽略 localStorage 中的 shelf，总是返回 config 的值。

## 三、bench_env 设计：任务评估的结构性问题

### 3.1 状态比对（StateComparator）依赖隐式约定

**问题一**：路径前缀过于宽松。`expected_changes = ["contacts"]` 会把 `wechat.contacts[0].avatar` 等变化都放过。

**问题二**：ID 字段的硬编码列表（`judge.py` 第 127 行）：
```python
ID_FIELDS = ["id", "wxid", "mid", "uid", "bookId", "chatId", "contactId", "messageId", "key"]
```
静态的，当新 App 引入新 ID 字段时必须修改中心文件。

### 3.2 crossapp3 任务中的 try/import 防御模式

软依赖问题——如果某 App 的 `app.py` 文件缺失，任务类不会报错，而是 `Alipay = None`，然后在 `is_successful()` 里悄悄失败。

### 3.3 crossapp3 重复实现父类逻辑

手动重写了 `BaseTask.setup()` 的核心逻辑，但跳过了 `warm_apps` 机制。

### 3.4 VLM judge 与状态 judge 缺乏统一接口

两套完全独立的评估路径，结构相同但语义不同。

## 四、配置替换机制：隐藏依赖破坏 bench_env 可配置性

### 4.1 `constants.ts` 与 `data/index.ts` 的边界模糊

`Railway12306/constants.ts` 中 service grid 包含了 `color: colors.service_icon_blue`——constants.ts 导入了 `res/colors.ts`。

### 4.2 AppStateRegistry.ts 中的硬编码逻辑是最大的配置陷阱

Alipay 的 `persistentReader` 硬编码了 18 个 preferences 默认值，这些值**不来自 defaults.json**，bench_env 即使替换 defaults.json 也无法影响它们——破坏了"配置替换"的核心承诺。

### 4.3 RedBook 的异步懒加载破坏了同步状态假设

bench_env 必须在读取 redbook 状态前调用 `__SIM__.waitForData(['redbook'])`，否则 entities 是空的。这是一个**隐式的初始化前置条件**。

### 4.4 Railway12306 的 `new Date()` 直接调用泄漏系统时间

全项目直接使用 `new Date()` 的地方多达 **176 处**，系统时间服务的封装远未彻底执行。

## 五、CSS 变量策略

### 5.1 `themeToCssVars.ts` 的运行时 DOM 注入是 Tailwind v4 的妥协产物

每次调用 `dimensToCssVars` 都会向 DOM 动态注入 CSS 规则。这意味着整个三层颜色系统的功能性，**依赖于一个运行时补丁**来修复框架 bug。

### 5.2 三层颜色系统在实践中没有完全落地

Clock 的 `res/colors.ts` 里大量区域注释为空。Notes 的 `res/colors.ts` 只有 5 个颜色，而它有 7 个页面。高质量迁移的 App（Wechat）和轻度使用的 App（Clock/Notes）之间存在巨大的一致性鸿沟。

---

## 六、导航声明模式

### 6.1 声明覆盖率只有 17/31 Apps

缺失的包括：Clock、Calendar、Browser、QQMusic、Notes、Weather、Gallery、Camera、Sms、ThemeStore

### 6.2 声明与实际代码的同步是手动维护

检查工具基于静态分析，但无法检查语义一致性（如 declaration 里说 `mode: 'push'`，代码里实际用了 `mode: 'replace'`）。

### 6.3 位置 action 的列表是硬编码的

Wechat 把所有可选地点硬编码进了 declaration，当 `data/defaults.json` 中的地点数据变化时，declaration 也必须手动同步。

---

## 七、数据架构：边界模糊导致多处一致性问题

### 7.1 persistentReader 复制了 defaults.json 的默认值

`AppStateRegistry.ts` 的 alipay reader 又复制了一遍 preferences 作为 fallback，两处数据需要手动保持同步。

### 7.2 `data/index.ts` 的复杂度分化

- 简单模式（Alipay、Railway12306）：3 行代码
- 复杂模式（Wechat）：100 行代码，包含时间解析、数据转换

---

## 八、可扩展性：28 个 App 后的架构压力

### 8.1 新增 App 需要修改至少 4 处核心文件

1. `os/types.ts`：`AppId` 和 `ImplementedAppId`
2. `os/data/appRegistry.tsx`：manifest + component
3. `os/AppStateRegistry.ts`：CONFIG + persistent reader
4. `bench_env/task/<app>/tasks.py`

### 8.2 App 状态读写的双重路径问题

运行时 `registerAppState` 和持久化 `persistentReaders` 两处实现理应返回相同结构，但 TypeScript 类型是 `() => any`，没有任何结构验证。

### 8.3 AgentBridge 和 mobile_gym.py 各自维护一份 APP_NAME_MAP

中文名到 appId 的映射在两处独立维护，需要手动保持同步。

## 核心设计哲学张力

最核心的设计哲学张力是：**这个项目既要对 Agent 透明（可静态分析的 navigation.declaration），又要对开发者友好（灵活的 React 代码），还要对 bench_env 可配置（替换 defaults.json）**。

这三个目标在实现层面产生了持续的矛盾：
- 静态分析要求字符串字面量，但 React 开发要求动态
- 配置替换要求数据集中，但应用开发要求就近管理
- AOSP 仿真要求结构对齐，但 Web 范式要求代码即数据

这些矛盾没有被系统性地解决，而是通过约定文档（CLAUDE.md）来约束，执行效果依赖开发者的自律。
