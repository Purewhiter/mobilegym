# mobile-gym 性能问题深度分析

---

## 1. React 渲染性能

### 1.1 Context 值对象未 memo 化 — 严重

**几乎所有 App 的 Context Provider 都在 value 处直接构造新对象**，导致每次 state 变更时，所有订阅该 Context 的组件强制重渲染。

```tsx
// apps/RedBook/context/RedBookContext.tsx, line 653
<RedBookContext.Provider value={{ ...state, updateHomeState, updatePublishDraft, ... }}>

// apps/Bilibili/context/BilibiliContext.tsx, line 338
<BilibiliContext.Provider value={{ user, updateUser, activeTab, setActiveTab, ...

// apps/Wechat/context/WechatGlobalContext.tsx, line 445
<WechatGlobalContext.Provider value={{ data, momentDraft, textMomentDraft, ...

// os/OSContext.tsx, line 787
<OSContext.Provider value={{ state, launchApp, goHome, showRecents, closeApp, ... }}>
```

上述 `value={{ ... }}` 每次渲染都产生新对象引用，React 会认为 context 已变更，触发所有 consumer 组件重渲染。正确做法是 `useMemo` 包裹 value 对象。

RedBook 有 **235 个** 地方调用 `useRedBook()`，Bilibili 有 **81 个**，任何微小的 state 变动（如 toggleLike）会触发这些组件全量重渲染。

### 1.2 BilibiliContext 函数未 useCallback 化 — 高

```tsx
// apps/Bilibili/context/BilibiliContext.tsx, lines 58–285
const updateUser = (updates: Partial<BilibiliUser>) => { ... };  // 每次渲染新建函数
const toggleFollow = (id: string | number) => { ... };
const isFollowing = (id: string | number) => { ... };
const toggleLike = (vid: string) => { ... };
```

配合 `value={{ ... }}` 直接传递，每次渲染都生成新函数引用，传递给 81 个消费组件。

### 1.3 OSContext 的 value 在每次 state 变更时重建 — 中

OSContext 是整个应用的根级 Context。`state` 包含 `runningApps`, `activeAppId`, `intentStack` 等，任何 OS 状态变更（切换 App、接收通知等）都会触发所有 `useOS()` 消费者重渲染。

### 1.4 dimensToCssVars 在每次渲染调用但未 memo — 中

```tsx
// apps/RedBook/RedBookApp.tsx, lines 58–64
const cssVars = {
  ...themeToCssVars(applySkinToThemeColors(themeColors)),
  ...dimensToCssVars(appColors, { prefix: '--app-c-' }),
  ...dimensToCssVars(appColorStates, { prefix: '--app-cs-' }),
  ...dimensToCssVars(dimens),
  ...dimensToCssVars(anim, { prefix: '--app-' }),
};
```

`dimensToCssVars` 除了产生 CSS var 对象，还会调用 `flushPendingRules()` 向 DOM `<style>` 标签写入规则，属于有副作用的计算，应用 `useMemo`。

### 1.5 RedBook 主页每次渲染过滤+分列大量数据 — 中

`feed` 最多包含来自 `crawled-notes.json` 的全部数据（可达数千条）。`.filter()` 在每次组件渲染时执行，没有包在 `useMemo` 中。

## 2. 内存管理

### 2.1 所有已启动的 App 始终常驻内存 — 设计决策，但风险高

```tsx
// os/SystemShell.tsx, lines 1102–1124
{/* Render ALL running apps - ALWAYS keep them mounted to preserve React state */}
{state.runningApps.map(appId => {
  style: { display: (state.activeAppId === appId && !state.isRecentsVisible) ? 'block' : 'none' }
  return <div key={appId} ... style={style}>{renderAppContent(appId)}</div>
})}
```

若用户启动了 Bilibili（60MB 数据）、X（90MB replies.json）、RedBook（15.9MB 数据）、Wechat，所有 Context 和组件树同时常驻内存。各 App 还在 `useEffect` 中持续运行 `setInterval`、注册 `MutationObserver` 等。

### 2.2 setState + localStorage 序列化在同一 useEffect — 中

```tsx
// apps/Wechat/context/WechatGlobalContext.tsx, lines 135–137
useEffect(() => {
  localStorage.setItem(STORAGE_KEY, JSON.stringify(data));
}, [data]);
```

`data` 是包含所有聊天记录、联系人、朋友圈的大对象。每次用户发一条消息，就触发完整的 JSON 序列化并写入 localStorage，**主线程同步阻塞**。同样模式在 24 个文件中出现。

### 2.3 RedBook useEffect 每次 state 变更都重新 registerAppState — 低

每次任何状态变更（like 一篇帖子）都会执行 `unregisterAppState` + `registerAppState`，闭包捕获了整个巨型 state。

## 3. Bundle 大小

### 3.1 大型 JSON 静态导入 — 严重

| 文件 | 大小 | 位置 |
|------|------|------|
| `catalog.products.json` | **6.1MB** | `apps/Ebay/pages/SearchPage.tsx:6` |
| `reddit_data.json` | 1MB | `apps/Reddit/data/index.ts:1` |
| `stationList.json` | 860KB | `apps/Railway12306/data/stations.ts:8` |
| `cityList.json` | 246KB | `apps/Railway12306/data/referenceData.ts:16` |
| `stationServices.json` | 111KB | `apps/Railway12306/data/referenceData.ts:13` |

对比之下，Bilibili（22MB）和 RedBook（16MB）已正确使用 `fetch()` 懒加载。

### 3.2 所有 App 的 manifest.ts 在启动时立即载入 — 低

28 个 App 的 manifest 全部静态导入。每个 manifest 又 `import { IcLauncher } from './res/icons'`，而 `res/icons.tsx` 包含该 App 所有 lucide-react 的导入。因此 28 个 App 的全量图标在应用启动时全量加载。

## 4. CSS/样式性能

### 4.1 大量 backdrop-blur 使用 — 中

Launcher 页面有超过 11 处 backdrop-blur，在低端设备上会明显卡顿。

### 4.2 dimensToCssVars 向 DOM 动态注入 CSS 规则 — 低~中

```tsx
// os/utils/themeToCssVars.ts, lines 50–51
styleTag.textContent += pendingRules.join('\n') + '\n';  // 字符串拼接追加
```

由于 `style.textContent +=` 是字符串拼接而非 `insertRule()`，每次追加都会触发整个 style block 的解析。

## 5. 数据处理

### 5.1 RedBook 的 `entities.notesById` 扩散导致深层 state 更新开销 — 中

```tsx
return {
  ...prev,
  entities: {
    ...prev.entities,
    notesById: {
      ...prev.entities.notesById,  // 展开整个 notesById（可达数千条）
      [noteId]: { ...prev.entities.notesById[noteId], likes: ... },
    },
  },
};
```

每次 `toggleLike` / `toggleCollect` / `addComment` 操作都展开整个 `notesById`（数千条），触发 235 个 consumer 组件重渲染。

---

## 6. 图片/资源加载

### 6.1 Reddit 图片无 lazy loading — 低

Bilibili、Gallery、X、Wechat 使用了 `loading="lazy"`，而 RedBook 的 `NoteItem` 和 Reddit 未使用。

### 6.2 RedBook 点击时主动预加载全部评论头像 — 中

每个 NoteItem 的 `beforeTrigger` 中通过 `requestIdleCallback` 预载所有评论头像。若一篇帖子有 100 条评论，点击时发出 100 个 HTTP 请求。

---

## 7. 滚动性能

### 7.1 Gallery onScroll 直接调用 setScrollTop — 中

每帧（~60次/秒）都触发 setState，导致 Gallery 组件树在每次滚动事件时重渲染。没有 requestAnimationFrame 包裹或 throttle。

### 7.2 无虚拟列表实现 — 中

整个项目没有使用任何虚拟滚动库。RedBook 的 `displayCount` 累积无上限，已渲染的节点不会卸载。

---

## 8. 启动性能

### 8.1 App 组件已正确懒加载（良好模式）

`appRegistry.tsx` 中所有 App 使用 `React.lazy(() => import(...))` 包裹，符合最佳实践。

### 8.2 RedBook 16MB 数据加载后触发大量 setState — 中

15.9MB 的数据在 App 首次挂载后请求，完成后一次性通过 setState 注入巨型 entities 对象。该 setState 触发 235 个 consumer 组件全量重渲染。

## 优先级总结

| 严重性 | 问题 | 位置 |
|--------|------|------|
| 严重 | Context value 无 memo（全量重渲染） | 全部 App Context 文件 |
| 严重 | Ebay 6.1MB JSON 静态 import | `SearchPage.tsx:6` |
| 高 | BilibiliContext 函数无 useCallback | `BilibiliContext.tsx:58–285` |
| 高 | 无虚拟列表，RedBook/Bilibili 大量 DOM 节点 | `HomePage.tsx` |
| 高 | localStorage 每次 state 变更同步序列化 | 24 处 |
| 中 | Railway12306 静态导入 1.2MB JSON | `stations.ts`, `referenceData.ts` |
| 中 | 滚动时无 throttle + 直接 setState | Gallery, RedBook |
| 中 | dimensToCssVars 未 memo，每次渲染重计算 | 所有 App Entry 文件 |
| 中 | entities.notesById 展开导致大对象克隆 | `RedBookContext.tsx:353` |
| 中 | 大量 backdrop-blur 图层合成开销 | Launcher.tsx（11处）|
| 低 | Reddit 图片无 lazy loading | Reddit 各页面 |
