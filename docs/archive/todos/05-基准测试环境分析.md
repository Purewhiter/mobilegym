# Benchmark Environment 深度分析报告

---

## 1. bench_env 整体结构

项目采用分层架构，结构清晰：

```
bench_env/
├── env/          # 环境层（Playwright 驱动）
│   ├── mobile_gym.py   # 核心环境类
│   ├── pool.py         # 并行环境池
│   └── base.py         # 基础抽象
├── agent/        # Agent 实现层
├── task/         # 任务定义层
│   ├── base.py         # BaseTask / BaseApp 基类
│   ├── judge.py        # JudgeInput / JudgeResult / StateComparator
│   ├── sampler.py      # 参数采样器
│   ├── registry.py     # 任务注册表
│   └── {app}/tasks.py  # 各 App 具体任务
└── runner/       # 运行控制层
    ├── base.py         # Controller / BaseRunner
    ├── serial.py       # 串行 runner
    └── parallel.py     # 并行 runner
```

## 2. 任务质量分析

### 2.1 评估判断 (Judge) 的健壮性

**CriteriaTask — 路由检查有假阳性风险**

`bench_env/task/common_tasks.py` 第 152-166 行：路由检查只做精确匹配，但不检查查询参数。

**AnswerTask — 数值检查假阳性（严重）**

```python
nums = re.findall(r'\d+', str(actual))
if nums:
    passed = any(float(n) == float(expected) for n in nums)
```

只要 agent 的回答中包含任意数字等于预期值就算通过。例如期望答案是 `5`，agent 回答 `"我找到了25个联系人，包含5个女性朋友"` 会通过。此外不支持小数匹配。

**CriteriaTask.get_expected_changes 漏洞**

把 criteria 的键直接当成 expected_changes，当任务实际上还会修改其他相关字段时，这些额外变化会被标记为意外副作用，产生假阴性。

### 2.2 crossapp 任务评估问题

**crossapp3 使用外部 HTTP 请求作为判断依据（严重）**

```python
def _url_content_contains(url: str, keyword: str) -> bool:
    r = requests.get(url, timeout=10, headers=headers)
```

评估时发起真实 HTTP 请求：网络不可用时所有依赖此函数的任务均判 False、外部网站内容随时可能变更、评估时间不确定。

**crossapp3 存在硬编码城市判断**

只特殊处理了北京和南京，其他城市走通用逻辑。

**_CrossApp3Task.setup() 绕过父类逻辑**

1. `env.reset()` 无 `app_ids` 参数，全量加载所有 App
2. 不调用 `env.warm_apps()`
3. 完全绕过了 `BaseTask.setup()` 中的 warm_apps 机制

## 3. Agent 类型分析

### 3.1 AutoGLMAgent — 解析健壮性问题

使用 `ast.parse` 解析 Python 函数调用。当模型输出中文引号或中文括号时会失败。

**更严重**：解析失败时 `return {"_finish": True, ...}`，任何无法解析的输出都被当成"任务完成"，产生大量假完成。

### 3.2 GenericAgentV2 — 历史消息格式问题

历史步骤没有包含截图，第一步之后的历史用户消息只有 `[Step N]`，完全没有上下文信息。

### 3.3 GelabAgent — Tab 分隔格式脆弱

Tab 分隔格式对模型输出非常敏感，模型只要输出空格而非 Tab，整个解析就会失败。

### 3.4 各 Agent 间的不一致性

| 特性 | AutoGLM | Generic | GenericV2 | GeLab |
|------|---------|---------|-----------|-------|
| 输出格式 | Python 函数调用 | JSON | XML+JSON | Tab分隔KV |
| 历史截图 | 无 | 无 | 无 | 无 |
| 路由信息 | 当前App名 | 完整路由 | 无 | 无 |
| INFO 回复支持 | 有 | 有 | 无 | 未知 |

**根本问题**：没有任何 agent 将历史步骤的截图传入消息。

## 4. 前后端通信协议

### 4.1 __SIM_INPUT__ 降级链可靠性

降级链将 `__SIM_INPUT__` 返回 False 和 `__SIM_INPUT__` 抛异常都映射到同样的 fallback。在 touchscreen 和 mouse fallback 情况下，行为可能与模拟器内部状态不同步。

### 4.2 状态获取的竞态条件

`delay_after_action` 默认 0.8 秒是经验值，对动画较慢的 UI 可能不够，没有等待 DOM 稳定的机制。

### 4.3 状态同步问题

`set_state` 不加 `reload=True` 时没有等待 React 重渲染。任务 `_prepare` 阶段用 `set_state` 注入测试数据时尤其危险。

### 4.4 _reset_sim 无法确认重置完成

1. `window.__SIM__.reset()` 是同步调用，但 React 状态更新是异步的
2. `wait_for_load_state("domcontentloaded")` 只等 DOM 加载，不等 React 渲染完成
3. 任何异常都被静默捕获，重置失败时后续任务会使用污染状态

## 5. AppStateRegistry 可靠性分析

### 5.1 运行时状态优先级潜在问题

优先使用运行时状态，但 App 在后台时可能已卸载并重新挂载。跨 app 操作时 localStorage 写入是异步的，可能有延迟。

### 5.2 bilibili 的 persistentReader 结构错误

```ts
user: data ?? BILIBILI_CONFIG.user  // Bug: 应为 data?.user
```

### 5.3 wechat_reading 强制使用 config 而非 localStorage

注释揭示这是权宜之计：因为 localStorage 里可能存了空数组。wechat_reading 书架相关的 benchmark 任务无法检测用户实际操作的影响。

---

## 6. 参数采样机制分析

### 6.1 种子可复现性问题

使用 `seed XOR crc32(task_id:i)` 生成种子，设计合理。但 `source` 类型的采样依赖环境状态，即使固定了 seed，如果环境状态不同，结果也不同。

### 6.2 pattern 采样功能极度有限

`_sample_pattern` 只支持 `\d{N}` 一种 pattern，其他所有正则都返回 None，无 warning。

---

## 7. crossapp 多 App 任务架构问题

### 7.1 三代 crossapp 实现不一致

crossapp、crossapp2、crossapp3 三个版本实现策略不统一，旧版本没有删除。

### 7.2 warm_apps 机制与 crossapp3 脱节

crossapp3 完全绕过 warm_apps 机制，每次都全量加载。

## 8. 可复现性分析

| 来源 | 位置 | 严重程度 |
|------|------|----------|
| 外部 HTTP 请求 | crossapp3 `_url_content_contains` | 严重 |
| 系统时间依赖 | crossapp3 `_now_ms()` | 中等 |
| localStorage 残留 | `_reset_sim` 无法保证完全清除 | 中等 |
| React 渲染时序 | `delay_after_action` 固定等待 | 中等 |
| VLM judge 非确定性 | LLM 输出随机性 | 低 |

---

## 9. 错误恢复机制

### 9.1 任务失败后的状态污染

异常时不重置环境，下一个任务使用同一个 env 实例的遗留状态。

### 9.2 EnvPool 启动失败处理不完整

部分 env 启动失败时只打日志继续运行，没有清理已成功启动的环境也没有终止。

### 9.3 browser 崩溃无恢复机制

一旦某个 page 崩溃，该 worker 的后续所有任务都会静默失败。

---

## 10. 关键改进建议汇总

**高优先级：**

1. AnswerTask 数值匹配修复：支持小数，且语义应更严格
2. AutoGLM 解析失败 fallback 修复：应改为返回 ABORT，而非 `_finish: True`
3. bilibili 持久化读取 bug 修复：`data?.user`
4. `_reset_sim` 加固：添加等待 React 状态恢复的逻辑
5. crossapp3 外部 HTTP 请求问题：应改为使用缓存内容或 mock 数据

**中优先级：**

6. EnvPool 启动失败处理：部分 env 失败时应抛异常
7. crossapp3 setup 统一：应使用 `warm_apps` 机制
8. `_sample_pattern` 扩展或明确文档
9. 竞态条件改善：`set_state` 后应等待 React 渲染完成
